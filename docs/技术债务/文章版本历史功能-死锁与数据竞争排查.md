## 1. 概述

本文档记录文章版本历史功能中可能存在的死锁和数据竞争问题，需要在后续版本中进行排查和修复。

---

## 2. 已知潜在问题

### 2.1 缓存与数据库操作

**问题位置**：`src/services/passage_version_service.rs`

**问题描述**：
- `list_versions()` 和 `get_version_count_cached()` 方法中，先从缓存读取，失败后再查数据库
- 缓存和数据库操作之间没有使用锁保护，可能存在竞态条件

**风险**：
- 缓存击穿（Cache Stampede）：多个并发请求同时发现缓存未命中，同时查询数据库
- 缓存与数据库数据不一致

**建议修复**：
- 实现分布式锁或本地锁来保护缓存未命中时的数据库查询
- 使用 `get_or_load` 模式（已有实现但未使用）

```rust
// 建议使用的方式
self.cache.get_or_load(key, async || {
    // 数据库查询
    Ok(Some(json_string))
}, ttl).await
```

---

### 2.2 Repository 层异步操作

**问题位置**：`src/db/repositories.rs`

**问题描述**：
- `PassageVersionRepository` 的方法使用 `async` 但内部使用同步的 `rusqlite` 操作
- 通过 `self.pool.get()?` 获取连接是同步的

**风险**：
- 阻塞异步运行时
- 可能导致线程饥饿

**建议修复**：
- 考虑使用 `sqlx` 或 `tokio-postgres` 等真正的异步数据库驱动
- 或使用 `tokio::task::spawn_blocking` 包装同步数据库操作

---

### 2.3 版本删除操作

**问题位置**：
- `src/services/passage_version_service.rs::delete_version()`
- `src/services/passage_version_service.rs::delete_versions_batch()`
- `src/db/repositories.rs::delete_batch()`

**问题描述**：
- 批量删除时，先删除数据库记录，再删除文件
- 如果文件删除失败，数据库记录已被删除，造成数据不一致

**风险**：
- orphaned files（数据库记录已删除但文件仍存在）
- 如果在文件删除过程中发生错误，可能导致部分删除

**建议修复**：
- 使用事务确保原子性（文件操作需要补偿事务）
- 实现删除日志和重试机制
- 考虑先删除文件再删除数据库记录

---

### 2.4 版本恢复操作

**问题位置**：
- `src/services/passage_version_service.rs::restore_version()`
- `src/services/passage_version_service.rs::soft_restore()`
- `src/services/passage_version_service.rs::hard_restore()`

**问题描述**：
- 恢复操作涉及：读取版本 → 更新数据库 → 写入文件 → 创建新版本记录 → 清除缓存
- 多个步骤之间没有事务保护

**风险**：
- 如果某个步骤失败，可能导致部分状态更新
- 并发恢复可能产生数据竞争

**建议修复**：
- 实现恢复锁机制，防止并发恢复同一文章
- 添加恢复操作日志和回滚机制

---

### 2.5 文件系统操作

**问题位置**：
- `src/services/passage_version_service.rs::write_history_file()`
- `src/services/passage_version_service.rs::read_history_file()`
- `src/services/passage_version_service.rs::delete_history_file()`

**问题描述**：
- 使用 `tokio::fs` 进行异步文件操作
- 但 `validate_path()` 和其他路径处理使用同步代码

**风险**：
- 路径遍历攻击防护不完整
- 文件操作与数据库操作之间没有原子性

---

### 2.6 缓存失效竞态

**问题位置**：
- `src/services/passage_version_service.rs::clear_version_cache()`
- `src/services/passage_version_service.rs::invalidate_version_cache()`

**问题描述**：
- 缓存清除使用通配符模式删除：`format!("version_list:{}:*", passage_id)`
- 多个并发请求可能导致缓存清除覆盖新写入的数据

**风险**：
- 缓存与数据库不一致
- 缓存雪崩

**建议修复**：
- 实现缓存版本号机制
- 使用缓存失效时间戳而非直接删除

## 3. 数据竞争风险点

### 3.1 读写竞争

| 方法 | 风险等级 | 描述 |
|------|---------|------|
| `save_version()` | 中 | 多个并发保存可能导致版本号重复 |
| `auto_save_version()` | 中 | 自动保存与手动保存并发 |
| `restore_version()` | 高 | 并发恢复可能覆盖彼此的更改 |
| `delete_version()` | 中 | 删除最新版本时的竞争 |

### 3.2 竞态条件场景

1. **版本号生成竞争**
   ```rust
   // 当前实现：先查询最新版本号，再插入新版本
   let version_number = self.get_next_version_number(passage_id).await?;
   // 多个并发请求可能获取相同的 version_number
   ```

2. **缓存击穿**
   ```rust
   // 当缓存过期时，多个请求同时发现缓存未命中
   if let Some(cached) = self.cache.get(&key).await {
       return Ok(cached);
   }
   // 多个请求同时执行数据库查询
   let versions = self.version_repo.list_versions(...).await?;
   ```

## 4. 建议的修复计划

### 4.1 短期修复（优先级：高）

1. **实现版本号生成的互斥保护**
   - 使用数据库的唯一约束
   - 或使用分布式锁

2. **使用缓存的 `get_or_load` 模式**
   - 替换手动缓存查询逻辑

3. **添加删除操作的事务支持**
   - 实现删除日志表
   - 添加重试机制

### 4.2 中期修复（优先级：中）

1. **迁移到异步数据库驱动**
   - 使用 `sqlx` 替代 `rusqlite`

2. **实现操作锁机制**
   - 为每篇文章添加读写锁
   - 防止并发恢复/删除冲突

3. **完善错误处理和回滚机制**
   - 添加操作日志
   - 实现补偿事务

### 4.3 长期修复（优先级：低）

1. **重新设计架构**
   - 考虑使用事件溯源模式
   - 实现最终一致性
